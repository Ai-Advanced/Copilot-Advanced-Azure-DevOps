## 이 챕터의 두 가지 실습 트랙

### Track A: Node.js Express API → Azure App Service (Zip Deploy)

PaaS 완전 관리형 서비스를 활용합니다. 컨테이너 관리 부담 없이 코드만 올리면 Azure가 런타임을 관리합니다. REST API, 백엔드 서비스, 내부 도구처럼 비교적 단순한 배포 요구사항에 어울립니다.

**이런 상황에 선택하세요:**
- 팀에 Docker/컨테이너 경험이 없거나 적을 때
- 빠르게 프로토타입을 프로덕션에 올려야 할 때
- OS 패치, 런타임 업그레이드를 직접 관리하고 싶지 않을 때
- 슬롯 스왑(무중단 배포)을 간단하게 쓰고 싶을 때

### Track B: Docker 컨테이너화 → ACR → Azure Container Apps

이미지를 직접 빌드하고 ACR에 저장한 뒤, Container Apps 위에서 실행합니다. 환경 일관성이 보장되고, 마이크로서비스 구성, 다양한 언어 혼용, 세밀한 스케일 제어가 필요할 때 강점이 드러납니다.

**이런 상황에 선택하세요:**
- 팀이 이미 Docker 워크플로에 익숙할 때
- 여러 언어/런타임이 혼재하는 마이크로서비스 아키텍처일 때
- KEDA 기반 이벤트 드리븐 스케일링이 필요할 때
- 로컬 환경과 프로덕션 환경을 동일하게 유지해야 할 때

## Track A: Node.js Express API → Azure App Service

소스·lock 파일·테스트·ESLint 설정·Bicep·승인/롤백 워크플로가 포함된
[실행 예제](../examples/01-web-app/README.md)를 제공합니다.
이하 코드는 학습용 설명이며, 실제 실행에서는 지원 런타임과 OIDC subject를 확인한 예제를 사용합니다.
2026-10-07 리허설에서는 `NODE:22-lts`를 사용했습니다. 슬롯 실습은 B1이 아닌 **S1 이상**이 필요합니다.

### Track A 개요 & 아키텍처

```
개발자 PC
    │
    │  git push (main 브랜치)
    ▼
GitHub Repository
    │
    │  GitHub Actions 트리거
    ▼
┌─────────────────────────────────────────────┐
│           GitHub Actions Runner              │
│                                             │
│  1. npm ci                                  │
│  2. npm test                                │
│  3. npm run build (있는 경우)               │
│  4. zip artifact 생성                       │
│  5. OIDC → Azure 로그인                     │
│  6. az webapp deploy (Zip Deploy)           │
└─────────────────────────────────────────────┘
    │
    │  OIDC 토큰 교환 (시크릿 없음)
    ▼
Azure Active Directory
    │
    │  권한 확인 후 액세스 토큰 발급
    ▼
Azure App Service
├── Production Slot  (main → 자동 배포)
└── Staging Slot     (검증 후 Swap)
```

워크플로는 두 개의 잡으로 분리됩니다. `build` 잡이 아티팩트를 만들고, `deploy` 잡이 `production` Environment 승인을 거쳐 배포합니다. 두 잡 사이에 아티팩트를 전달하므로 배포 잡은 소스코드 체크아웃 없이 동작합니다.

### 프로젝트 스캐폴딩 (Copilot으로)

#### Copilot Chat 프롬프트

VS Code Copilot Chat을 열고 다음 프롬프트를 입력합니다.

```
간단한 Express API 생성해줘.
- /health GET 엔드포인트: { status: "ok", timestamp: ISO 날짜 }
- /users GET: 인메모리 유저 목록 반환
- /users POST: Zod로 { name: string, email: string } 검증 후 추가
- jest + supertest로 각 엔드포인트 테스트 포함
- TypeScript 아님, 순수 JS (CommonJS)
- 포트는 환경변수 PORT 또는 3000
```

Copilot이 생성한 결과를 기반으로 다음과 같은 구조를 만듭니다.

#### 핵심 소스코드: `src/app.js`

```js
'use strict';

const express = require('express');
const { z } = require('zod');

const app = express();
app.use(express.json());

// 인메모리 스토어
const users = [
  { id: 1, name: 'Alice', email: 'alice@example.com' },
  { id: 2, name: 'Bob',   email: 'bob@example.com'   },
];

// GET /health
app.get('/health', (req, res) => {
  res.json({ status: 'ok', timestamp: new Date().toISOString() });
});

// GET /users
app.get('/users', (req, res) => {
  res.json(users);
});

// POST /users
const userSchema = z.object({
  name:  z.string().min(1),
  email: z.string().email(),
});

app.post('/users', (req, res) => {
  const result = userSchema.safeParse(req.body);
  if (!result.success) {
    return res.status(400).json({ errors: result.error.flatten() });
  }
  const newUser = { id: users.length + 1, ...result.data };
  users.push(newUser);
  res.status(201).json(newUser);
});

module.exports = app;
```

#### 서버 진입점: `src/server.js`

```js
'use strict';

const app = require('./app');

const PORT = process.env.PORT || 3000;
app.listen(PORT, () => {
  console.log(`Server listening on port ${PORT}`);
});
```

#### 테스트: `tests/app.test.js`

```js
'use strict';

const request = require('supertest');
const app     = require('../src/app');

describe('GET /health', () => {
  it('status ok 반환', async () => {
    const res = await request(app).get('/health');
    expect(res.statusCode).toBe(200);
    expect(res.body.status).toBe('ok');
  });
});

describe('GET /users', () => {
  it('배열 반환', async () => {
    const res = await request(app).get('/users');
    expect(res.statusCode).toBe(200);
    expect(Array.isArray(res.body)).toBe(true);
  });
});

describe('POST /users', () => {
  it('유효한 데이터로 유저 생성', async () => {
    const res = await request(app)
      .post('/users')
      .send({ name: 'Charlie', email: 'charlie@example.com' });
    expect(res.statusCode).toBe(201);
    expect(res.body.name).toBe('Charlie');
  });

  it('잘못된 이메일로 400 반환', async () => {
    const res = await request(app)
      .post('/users')
      .send({ name: 'Dave', email: 'not-an-email' });
    expect(res.statusCode).toBe(400);
  });
});
```

### Azure 리소스 프로비저닝 (Track A)

로컬 터미널에서 Azure CLI로 리소스를 생성합니다. 변수를 먼저 설정하면 명령이 깔끔해집니다.

```bash
# 변수 설정
RG="rg-myapp-prod"
LOCATION="koreacentral"
PLAN="asp-myapp-prod"
WEBAPP="myapp-express-20240824"   # 전역 고유 이름

# 리소스 그룹 생성
az group create \
  --name "$RG" \
  --location "$LOCATION"

# App Service Plan (Linux, B1)
az appservice plan create \
  --name "$PLAN" \
  --resource-group "$RG" \
  --location "$LOCATION" \
  --sku B1 \
  --is-linux

# Web App (지원되는 런타임은 az webapp list-runtimes --os linux로 확인)
az webapp create \
  --name "$WEBAPP" \
  --resource-group "$RG" \
  --plan "$PLAN" \
  --runtime "NODE:22-lts"

# 애플리케이션 설정 (환경변수)
az webapp config appsettings set \
  --name "$WEBAPP" \
  --resource-group "$RG" \
  --settings \
    NODE_ENV="production" \
    WEBSITE_RUN_FROM_PACKAGE="1"
```

`WEBSITE_RUN_FROM_PACKAGE=1`을 설정하면 App Service가 Zip 패키지를 마운트해서 실행합니다. 파일을 직접 덮어쓰지 않으므로 배포 속도가 빠르고 파일 잠금 문제도 없습니다.

### Federated Credential 등록 (Track A)

등록 전 [Ch.7 subject 확인 안내](ch07_GitHub_Actions_Azure_통합_CICD.md#3-1-subject-클레임-패턴-비교)를 따릅니다.
아래 이름 기반 subject를 immutable subject 저장소에 그대로 적용하면 인증이 실패합니다.

#### 앱 등록 및 서비스 프린시펄 생성

```bash
GITHUB_ORG="Ai-Advanced"
GITHUB_REPO="my-express-api"
APP_NAME="sp-myapp-prod"

# 앱 등록
APP_ID=$(az ad app create \
  --display-name "$APP_NAME" \
  --query appId -o tsv)

# 서비스 프린시펄 생성
SP_OBJ_ID=$(az ad sp create \
  --id "$APP_ID" \
  --query id -o tsv)

echo "APP_ID: $APP_ID"
echo "SP_OBJ_ID: $SP_OBJ_ID"
```

#### Federated Credential 등록

GitHub Actions가 `production` Environment에서 실행될 때만 토큰을 발급받도록 Subject를 범위 지정합니다.

```bash
# credential.json 생성
cat > /tmp/credential.json <<EOF
{
  "name": "github-production-env",
  "issuer": "https://token.actions.githubusercontent.com",
  "subject": "repo:${GITHUB_ORG}/${GITHUB_REPO}:environment:production",
  "audiences": ["api://AzureADTokenExchange"],
  "description": "GitHub Actions production environment"
}
EOF

# Federated Credential 등록
az ad app federated-credential create \
  --id "$APP_ID" \
  --parameters /tmp/credential.json
```

#### 구독에 Contributor 권한 부여

```bash
SUBSCRIPTION_ID=$(az account show --query id -o tsv)

az role assignment create \
  --assignee-object-id "$SP_OBJ_ID" \
  --assignee-principal-type ServicePrincipal \
  --role "Contributor" \
  --scope "/subscriptions/${SUBSCRIPTION_ID}/resourceGroups/${RG}"
```

> **최소 권한 원칙**: 구독 전체가 아닌 리소스 그룹 범위로 권한을 부여합니다.

### GitHub Repo 설정 (Track A)

#### `production` Environment 생성

1. GitHub 리포지터리 → **Settings** → **Environments** → **New environment**
2. 이름: `production`
3. **Required reviewers** 체크 후 리뷰어 추가 (최소 1명 권장)
4. **Wait timer**: 0분 (필요 시 지연 배포 가능)

#### Environment Secrets 등록

**Settings → Environments → production → Environment secrets**에서 다음 4개를 등록합니다.

| Secret 이름 | 값 |
|---|---|
| `AZURE_CLIENT_ID` | 앞서 출력한 `$APP_ID` |
| `AZURE_TENANT_ID` | `az account show --query tenantId -o tsv` |
| `AZURE_SUBSCRIPTION_ID` | `az account show --query id -o tsv` |
| `AZURE_WEBAPP_NAME` | `myapp-express-20240824` |

#### Branch Protection Rule 확인

**Settings → Branches → Add branch ruleset** (또는 기존 규칙 수정):

- `main` 브랜치: Pull Request 필수, 상태 검사(CI) 통과 필수
- Force push 금지

### 워크플로 작성: `deploy-app-service.yml`

`.github/workflows/deploy-app-service.yml` 전문입니다. Copilot Chat에 다음 프롬프트로 초안을 생성하고 수정합니다.

```
GitHub Actions 워크플로 만들어줘.
- main 브랜치 push 시 트리거
- build 잡: npm ci, npm test, zip 아티팩트 생성
- deploy 잡: production Environment 사용, OIDC로 Azure 로그인,
  azure/webapps-deploy@v3으로 배포
- Node 22, ubuntu-latest
- 잡 간 아티팩트 전달
```

```yaml
name: Deploy to Azure App Service

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  id-token: write   # OIDC 토큰 발급에 필요

jobs:
  # ── 1단계: 빌드 & 테스트 ────────────────────────────────────
  build:
    name: Build & Test
    runs-on: ubuntu-latest

    steps:
      - name: Checkout source
        uses: actions/checkout@v4

      - name: Setup Node.js 22
        uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Run tests
        run: npm test

      - name: Run lint
        run: npm run lint

      - name: Create deployment package
        run: |
          # 프로덕션 의존성만 포함한 zip 생성
          npm ci --omit=dev
          zip -r deploy.zip . \
            --exclude "*.git*" \
            --exclude "tests/*" \
            --exclude "*.zip"

      - name: Upload artifact
        uses: actions/upload-artifact@v4
        with:
          name: app-package
          path: deploy.zip
          retention-days: 1

  # ── 2단계: Azure App Service 배포 ───────────────────────────
  deploy:
    name: Deploy to Production
    runs-on: ubuntu-latest
    needs: build
    environment:
      name: production
      url: https://${{ secrets.AZURE_WEBAPP_NAME }}.azurewebsites.net

    steps:
      - name: Download artifact
        uses: actions/download-artifact@v4
        with:
          name: app-package

      - name: Azure Login (OIDC)
        uses: azure/login@v2
        with:
          client-id:       ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id:       ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}

      - name: Deploy to Azure Web App
        uses: azure/webapps-deploy@v3
        with:
          app-name:    ${{ secrets.AZURE_WEBAPP_NAME }}
          package:     deploy.zip

      - name: Health check
        run: |
          sleep 30
          STATUS=$(curl -s -o /dev/null -w "%{http_code}" \
            https://${{ secrets.AZURE_WEBAPP_NAME }}.azurewebsites.net/health)
          if [ "$STATUS" != "200" ]; then
            echo "Health check failed: HTTP $STATUS"
            exit 1
          fi
          echo "Health check passed: HTTP $STATUS"
```

**주요 포인트:**

- `permissions.id-token: write`가 없으면 OIDC 토큰 발급 자체가 실패합니다.
- `environment: name: production`을 선언해야 Environment Secrets에 접근하고 Reviewer 게이트가 동작합니다.
- `url` 필드는 Actions UI에 "배포된 URL" 링크로 표시됩니다.
- `deploy` 잡은 소스코드를 체크아웃하지 않습니다. 아티팩트만 내려받아 배포하므로 보안 면에서도 깔끔합니다.

### 첫 배포 실행 & 검증 (Track A)

#### 배포 트리거

```bash
git add .github/workflows/deploy-app-service.yml
git commit -m "feat: add App Service deploy workflow"
git push origin main
```

#### Actions 탭 흐름 확인

1. GitHub → **Actions** 탭에서 워크플로 실행 클릭
2. **Build & Test** 잡이 먼저 완료되는지 확인합니다.
3. **Deploy to Production** 잡에서 "Review deployments" 버튼이 나타나면 리뷰어가 승인합니다.
4. 승인 후 배포 잡이 시작됩니다. `Azure Login (OIDC)` 스텝에서 시크릿 노출 없이 로그인되는 것을 확인합니다.
5. `Health check` 스텝이 `HTTP 200`을 출력하면 배포 완료입니다.

#### 엔드포인트 검증

```bash
WEBAPP_NAME="myapp-express-20240824"
BASE_URL="https://${WEBAPP_NAME}.azurewebsites.net"

# Health check
curl -s "${BASE_URL}/health" | jq .
# 기댓값: { "status": "ok", "timestamp": "2024-08-24T..." }

# 유저 목록
curl -s "${BASE_URL}/users" | jq .

# 유저 생성
curl -s -X POST "${BASE_URL}/users" \
  -H "Content-Type: application/json" \
  -d '{"name":"Charlie","email":"charlie@example.com"}' | jq .
```

### 슬롯 배포로 확장 (심화 선택 사항)

App Service의 Staging Slot을 활용하면 프로덕션 트래픽 없이 먼저 검증하고 스왑할 수 있습니다.

#### Staging Slot 생성

```bash
# staging 슬롯 추가 (Standard 플랜 이상 필요, B1은 지원 안 함)
# B1에서 테스트하려면 S1으로 업그레이드 필요
az appservice plan update \
  --name "$PLAN" \
  --resource-group "$RG" \
  --sku S1

az webapp deployment slot create \
  --name "$WEBAPP" \
  --resource-group "$RG" \
  --slot staging
```

#### 워크플로 슬롯 배포 스텝 추가

```yaml
      - name: Deploy to Staging Slot
        uses: azure/webapps-deploy@v3
        with:
          app-name: ${{ secrets.AZURE_WEBAPP_NAME }}
          slot-name: staging
          package:  deploy.zip

      - name: Validate staging
        run: |
          sleep 20
          curl -sf "https://${{ secrets.AZURE_WEBAPP_NAME }}-staging.azurewebsites.net/health"

      - name: Swap staging to production
        uses: azure/CLI@v2
        with:
          inlineScript: |
            az webapp deployment slot swap \
              --name ${{ secrets.AZURE_WEBAPP_NAME }} \
              --resource-group ${{ secrets.AZURE_RG }} \
              --slot staging \
              --target-slot production
```

스왑은 순간적으로 일어납니다. 라우팅이 전환되는 시간 동안 기존 프로덕션 코드는 그대로 Staging Slot으로 넘어가므로, 문제가 생기면 다시 스왑하는 것으로 롤백됩니다.

### Dockerfile 작성 (Copilot 활용)

#### Copilot Chat 프롬프트

```
Node.js 20 앱을 위한 프로덕션급 multi-stage Dockerfile 만들어줘.
- 빌더 스테이지: 의존성 설치
- 프로덕션 스테이지: node:20-alpine, non-root user(node) 실행
- 이미지 사이즈 최소화 (devDependencies 제외)
- HEALTHCHECK 포함
- 포트 3000
```

#### `Dockerfile`

```dockerfile
# ── Stage 1: 빌더 ────────────────────────────────────────────
FROM node:20-alpine AS builder

WORKDIR /app

# package 파일만 먼저 복사해 레이어 캐시를 활용
COPY package*.json ./
RUN npm ci --omit=dev

# ── Stage 2: 프로덕션 이미지 ─────────────────────────────────
FROM node:20-alpine AS production

# 보안: non-root user로 실행
# node:20-alpine에는 'node' 유저(uid 1000)가 기본 포함
WORKDIR /app

# 빌더 스테이지에서 node_modules만 복사
COPY --from=builder /app/node_modules ./node_modules

# 소스코드 복사 (소유권을 node 유저로 지정)
COPY --chown=node:node src/ ./src/
COPY --chown=node:node package.json ./

USER node

EXPOSE 3000

HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD wget -qO- http://localhost:3000/health || exit 1

CMD ["node", "src/server.js"]
```

**핵심 포인트:**

- `--omit=dev`로 devDependencies를 완전히 제외해 이미지 크기를 줄입니다.
- `COPY --from=builder`로 빌더 스테이지의 빌드 도구(npm, 캐시)가 최종 이미지에 포함되지 않습니다.
- `USER node`로 root 권한 없이 프로세스를 실행합니다.
- `HEALTHCHECK`는 Container Apps 런타임이 컨테이너 상태를 판단하는 데 사용됩니다.

### GitHub Actions 워크플로: `deploy-container-app.yml`

`.github/workflows/deploy-container-app.yml` 전문입니다.

```yaml
name: Build & Deploy Container App

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  id-token: write   # OIDC 필수

env:
  REGISTRY: ${{ secrets.AZURE_ACR_NAME }}.azurecr.io
  IMAGE_NAME: my-express-api

jobs:
  # ── 1단계: 이미지 빌드 & ACR 푸시 ──────────────────────────
  build-and-push:
    name: Build & Push Image
    runs-on: ubuntu-latest

    outputs:
      image-tag: ${{ steps.meta.outputs.version }}

    steps:
      - name: Checkout source
        uses: actions/checkout@v4

      - name: Azure Login (OIDC)
        uses: azure/login@v2
        with:
          client-id:       ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id:       ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}

      - name: Login to ACR
        run: az acr login --name ${{ secrets.AZURE_ACR_NAME }}

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Generate image metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=sha,prefix=sha-,format=short
            type=raw,value=latest,enable={{is_default_branch}}

      - name: Build and push image
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=registry,ref=${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:latest
          cache-to:   type=inline
          provenance: false

  # ── 2단계: Container Apps 배포 ──────────────────────────────
  deploy:
    name: Deploy to Container Apps
    runs-on: ubuntu-latest
    needs: build-and-push
    environment:
      name: container-prod
      url: https://ca-myapp-prod.happypebble-12345.koreacentral.azurecontainerapps.io

    steps:
      - name: Azure Login (OIDC)
        uses: azure/login@v2
        with:
          client-id:       ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id:       ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}

      - name: Deploy to Azure Container Apps
        uses: azure/container-apps-deploy-action@v2
        with:
          resourceGroup:      ${{ secrets.AZURE_RG }}
          containerAppName:   ${{ secrets.AZURE_CONTAINER_APP_NAME }}
          imageToDeploy: >
            ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:sha-${{ github.sha }}

      - name: Show new revision
        run: |
          az containerapp revision list \
            --name ${{ secrets.AZURE_CONTAINER_APP_NAME }} \
            --resource-group ${{ secrets.AZURE_RG }} \
            --query "[].{name:name,active:properties.active,traffic:properties.trafficWeight}" \
            -o table
```

**이미지 태그 전략:**

- `sha-<short-sha>`: Git 커밋과 이미지를 1:1로 추적합니다. 롤백 시 정확한 이미지를 지정할 수 있습니다.
- `latest`: 기본 브랜치(`main`)의 최신 이미지를 가리킵니다. 빠른 참조용입니다.
- 두 태그를 동시에 푸시하므로 추적성과 편의성을 모두 챙깁니다.

**BuildKit 캐시:**

`cache-from: type=registry`를 사용해 ACR에 저장된 이전 `latest` 이미지를 캐시 소스로 활용합니다. 변경되지 않은 레이어는 다시 빌드하지 않으므로 빌드 시간이 단축됩니다.

#### 트래픽 분할 (Blue/Green) 개념

Container Apps의 Revision 모드를 `Multiple`로 설정하면 두 Revision에 트래픽을 나눌 수 있습니다.

```bash
# Revision 모드를 Multiple로 변경
az containerapp update \
  --name "$CA_NAME" \
  --resource-group "$RG" \
  --revision-suffix "v2" \
  --traffic-weight "latest=20,<이전-revision-이름>=80"
```

20%의 요청을 새 버전으로 보내면서 오류율을 모니터링하고, 문제가 없으면 100%로 전환합니다. 이것이 Blue/Green 배포의 핵심입니다. 문제가 생기면 트래픽을 즉시 이전 Revision으로 되돌릴 수 있습니다.

## 실습 과제

### 과제 A: App Service 슬롯 배포 자동화

다음 조건을 만족하는 워크플로를 작성하세요.

1. `main` 브랜치 push 시 `staging` 슬롯에 먼저 배포합니다.
2. `/health` 엔드포인트로 30초 대기 후 상태를 검증합니다.
3. 검증 성공 시 `production` Environment 승인을 거쳐 Slot Swap을 실행합니다.
4. Swap 후 프로덕션 URL에서 `/health`를 재검증합니다.

**힌트**: `azure/CLI@v2` 액션의 `inlineScript`로 `az webapp deployment slot swap` 명령을 실행합니다.

### 과제 B: Container Apps 점진적 트래픽 전환

다음 조건을 만족하는 워크플로를 작성하세요.

1. 새 이미지를 빌드해 ACR에 푸시합니다.
2. 새 Revision에 트래픽 20%만 할당한 채 배포합니다.
3. 5분 대기 후 Azure CLI로 `/health` 엔드포인트를 10회 호출해 오류율을 측정합니다.
4. 오류율이 5% 미만이면 트래픽을 100%로 전환하고, 초과하면 이전 Revision으로 복구합니다.

**힌트**: `az containerapp ingress traffic set` 명령과 쉘 스크립트 조건문을 조합합니다.

## 트러블슈팅

| 증상 | 원인 | 해결 방법 |
|---|---|---|
| `OIDC: request failed` | Federated Credential의 Subject가 다름 | Subject의 Environment 이름이 GitHub Environment 이름과 정확히 일치하는지 확인 |
| `az login: No subscriptions found` | 서비스 프린시펄에 구독 접근 권한 없음 | `az role assignment create`로 Contributor 권한 재부여 |
| App Service 배포 후 `Application Error` 페이지 | `WEBSITE_RUN_FROM_PACKAGE` 미설정 또는 `package.json` `start` 스크립트 누락 | `az webapp config appsettings set`으로 설정 확인, `npm start` 명령 검증 |
| `npm test` 실패로 빌드 잡 중단 | 테스트 코드 오류 또는 포트 충돌 | 테스트에서 `supertest`가 포트를 직접 열지 않는지 확인, `app.js`에서 `listen` 호출 분리 |
| Docker 빌드 실패: `COPY failed` | `.dockerignore`가 필요한 파일을 제외함 | `.dockerignore` 내용 점검, `src/` 폴더가 제외되지 않았는지 확인 |
| ACR 이미지 푸시 실패: `unauthorized` | 서비스 프린시펄에 `AcrPush` 권한 없음 | `az role assignment create --role AcrPush` 재실행 |
| Container App 시작 안 됨: `Replica failed` | 이미지 `HEALTHCHECK` 실패 또는 포트 불일치 | `az containerapp logs show`로 stderr 확인, `--target-port` 값이 앱 실제 포트와 일치하는지 확인 |
| Managed Identity ACR Pull 실패 | `AcrPull` 역할 미부여 또는 레지스트리 연결 설정 누락 | `az containerapp registry set --identity system` 실행 여부 확인 |
| Slot Swap 후 사용자가 503 경험 | ARR Affinity 쿠키 충돌 | 무상태 앱이면 ARR Affinity를 비활성화 (`az webapp update --client-affinity-enabled false`) |
| GitHub Actions 워크플로가 Environment 승인 없이 실행됨 | `environment:` 필드 누락 | `deploy` 잡에 `environment: name: production` 추가 확인 |

## 현업 팁

1. **이미지 태그에 `latest`만 쓰지 마세요.** `latest`는 "가장 최근"을 보장하지 않습니다. Git SHA 태그를 함께 붙여야 어떤 커밋이 프로덕션에 있는지 추적할 수 있습니다.

2. **ACR 관리자 계정은 활성화하지 마세요.** 자격 증명이 정적이라 로테이션이 어렵습니다. Managed Identity나 서비스 프린시펄 + Federated Credential 조합을 쓰세요.

3. **Health Check 엔드포인트는 의존성까지 확인하세요.** `/health`가 단순히 `{ status: "ok" }`만 반환하면 DB 연결이 끊겨도 성공으로 보입니다. DB ping, 외부 API 연결 상태를 포함한 응답을 반환하는 것이 좋습니다.

4. **빌드 잡과 배포 잡을 반드시 분리하세요.** 하나의 잡으로 합치면 빌드 실패 시에도 배포가 시작될 수 있고, 아티팩트 재사용도 불가능합니다. 잡 분리가 보안과 재현성 모두에 유리합니다.

5. **Container Apps의 `--min-replicas 0` 설정은 신중하게 쓰세요.** 비용은 절감되지만 콜드 스타트가 발생합니다. 프로덕션 API에서는 최소 1개 이상의 Replica를 유지하는 것을 권장합니다.

6. **Federated Credential의 Subject 범위를 좁히세요.** `repo:org/repo:ref:refs/heads/main`처럼 브랜치까지 범위를 지정하면 다른 브랜치의 워크플로가 프로덕션 자격 증명을 사용하는 것을 막을 수 있습니다.

7. **워크플로 파일을 변경할 때는 PR로 진행하세요.** `.github/workflows/` 파일을 직접 main에 push하면 검토 없이 배포 파이프라인이 바뀝니다. Branch Protection Rule에 PR 필수 조건을 설정하고, 워크플로 변경도 코드 리뷰 대상에 포함하세요.

## 정리 & 다음 단계

이 챕터에서는 두 가지 완전한 배포 시나리오를 처음부터 끝까지 다뤘습니다.

**Track A**에서는 Express API를 스캐폴딩하고, App Service에 Zip Deploy 방식으로 배포하는 워크플로를 완성했습니다. Federated Credential로 시크릿 없는 OIDC 로그인을 구현하고, Staging Slot Swap으로 무중단 배포를 경험했습니다.

**Track B**에서는 Multi-stage Dockerfile로 경량 이미지를 만들고, ACR에 SHA 태그로 푸시한 뒤, Container Apps에 배포했습니다. Managed Identity로 admin 계정 없이 ACR Pull 권한을 부여하고, Revision 기반 트래픽 분할로 Blue/Green 배포의 기초를 익혔습니다.

두 트랙 모두 Copilot Chat을 적극 활용해 코드 생성 시간을 단축했습니다. 반복적인 YAML 작성, Dockerfile 패턴, 테스트 코드를 Copilot이 초안을 잡아주면 엔지니어는 검토와 수정에 집중할 수 있습니다.

다음 챕터에서는 이 배포 파이프라인에 보안, 모니터링, 롤백 자동화를 추가합니다.
