## 2. GitHub Advanced Security (GHAS) 3대 기능 실전

GHAS는 GitHub Enterprise 또는 Public 리포지토리에서 무료로 사용할 수 있는 보안 스캔 플랫폼입니다. 세 가지 핵심 기능을 순서대로 살펴봅니다.

### 2-1. Code Scanning (CodeQL)

CodeQL은 코드를 데이터베이스로 변환한 뒤 쿼리로 취약점 패턴을 찾는 정적 분석 엔진입니다. Actions 워크플로에 아래처럼 추가하면 PR마다 자동으로 실행됩니다.

```yaml
# .github/workflows/codeql.yml
name: CodeQL Analysis

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]
  schedule:
    - cron: '0 2 * * 1'   # 매주 월요일 02:00 UTC 정기 스캔

permissions:
  contents: read
  security-events: write   # SARIF 결과 업로드에 필요

jobs:
  analyze:
    name: Analyze (${{ matrix.language }})
    runs-on: ubuntu-latest

    strategy:
      fail-fast: false
      matrix:
        language: [javascript-typescript, python]
        # 지원 언어: c-cpp, csharp, go, java-kotlin, ruby, swift

    steps:
      - name: Checkout repository
        uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683  # v4.2.2

      - name: Initialize CodeQL
        uses: github/codeql-action/init@4f3212b61783c3c68e8309a0f18a699764811cda  # v3.26.1
        with:
          languages: ${{ matrix.language }}
          queries: security-extended   # 기본 security-and-quality보다 더 광범위한 쿼리셋

      - name: Autobuild
        uses: github/codeql-action/autobuild@4f3212b61783c3c68e8309a0f18a699764811cda  # v3.26.1

      - name: Perform CodeQL Analysis
        uses: github/codeql-action/analyze@4f3212b61783c3c68e8309a0f18a699764811cda  # v3.26.1
        with:
          category: '/language:${{ matrix.language }}'
```

결과는 **Security > Code scanning** 탭에서 확인하고, 높음(High) 이상 심각도는 PR 머지를 차단하도록 Branch Protection Rule에 `Required status checks`로 등록하는 것을 권장합니다.

### 2-2. Secret Scanning + Push Protection

Secret Scanning은 커밋에 API 키, 연결 문자열, 토큰이 포함되면 즉시 감지하고 소유자에게 알립니다. Push Protection은 한 발 더 나아가 **푸시 자체를 차단**합니다.

**조직 단위 활성화 (Settings > Code security and analysis)**:

```bash
# GitHub CLI로 조직의 모든 리포지토리에 Secret Scanning 활성화
gh api \
  --method PATCH \
  /orgs/Ai-Advanced \
  -f secret_scanning='{"status":"enabled"}' \
  -f secret_scanning_push_protection='{"status":"enabled"}'
```

**알림 처리 흐름**:

1. GitHub이 시크릿을 감지하면 리포지토리 Security 탭에 알림이 생성됩니다.
2. 담당자는 `Revoke and rotate` 또는 `Mark as used in tests` 중 하나를 선택합니다.
3. 실제 유출이면 즉시 해당 시크릿을 무효화하고 Key Vault에서 새 값을 발급합니다.
4. Push Protection을 우회했다면 커밋을 `git filter-repo`로 히스토리에서 제거합니다.

### 2-3. Dependabot

`.github/dependabot.yml` 파일 하나로 npm, Docker, GitHub Actions 세 생태계의 의존성 업데이트를 자동화합니다.

```yaml
# .github/dependabot.yml
version: 2

updates:
  # npm 패키지 업데이트
  - package-ecosystem: npm
    directory: /
    schedule:
      interval: weekly
      day: monday
      time: '09:00'
      timezone: Asia/Seoul
    open-pull-requests-limit: 10
    groups:
      dev-dependencies:
        dependency-type: development
    ignore:
      - dependency-name: 'some-legacy-package'
        versions: ['> 2.0.0']
    labels:
      - dependencies
      - automated

  # Docker 베이스 이미지 업데이트
  - package-ecosystem: docker
    directory: /
    schedule:
      interval: weekly
      day: tuesday
      time: '09:00'
      timezone: Asia/Seoul
    open-pull-requests-limit: 5
    labels:
      - dependencies
      - docker

  # GitHub Actions 버전 업데이트
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly
      day: wednesday
      time: '09:00'
      timezone: Asia/Seoul
    open-pull-requests-limit: 10
    labels:
      - dependencies
      - github-actions
```

Dependabot이 생성한 PR은 CodeQL 스캔과 테스트를 통과하면 `auto-merge` 정책을 적용해 리뷰 부담을 줄일 수 있습니다.

### 2-4. Copilot Autofix

GitHub Copilot Autofix는 CodeQL이 취약점을 발견하면 PR 코멘트에 수정 코드를 제안하는 기능입니다. 동작 흐름은 다음과 같습니다.

1. CodeQL이 SQL 인젝션, XSS 같은 취약점을 탐지합니다.
2. Copilot이 해당 코드를 분석해 안전한 대안 코드를 생성합니다.
3. PR 코멘트에 **"Apply this suggestion"** 버튼이 나타납니다.
4. 리뷰어가 승인하면 커밋이 자동으로 추가됩니다.

> **주의**: Autofix 제안도 반드시 사람이 검토해야 합니다. 컨텍스트를 모르는 상태로 적용하면 비즈니스 로직이 깨질 수 있습니다.

## 3. GitHub Actions 자체 보안

워크플로 자체도 공격 대상이 됩니다. 공급망 공격, 권한 과잉, 잘못 설정된 트리거가 대표적인 위협입니다.

### 3-1. Third-party Actions SHA 고정

태그(`v3`, `v4`)는 리포지토리 소유자가 언제든 가리키는 커밋을 바꿀 수 있어 신뢰할 수 없습니다. **불변 SHA**로 고정해야 합니다.

```yaml
steps:
  # 태그 사용 — 위험 (태그가 다른 커밋을 가리킬 수 있음)
  # - uses: actions/checkout@v4

  # SHA 고정 — 권장
  - name: Checkout
    uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683  # tag: v4.2.2

  - name: Setup Node.js
    uses: actions/setup-node@39370e3970a6d050c480ffad4ff0ed4d3fdee5af  # tag: v4.1.0

  - name: Upload artifact
    uses: actions/upload-artifact@65c4c4a1ddee5b72f698fdd19549f0f0fb45cf08  # tag: v4.4.3
```

SHA는 [github.com/actions/checkout/releases](https://github.com/actions/checkout/releases) 또는 `gh release view`로 확인합니다.

### 3-2. `permissions:` 최소 권한 원칙

워크플로 최상단 또는 job 단위로 권한을 명시적으로 선언합니다. 선언하지 않으면 기본값이 `write-all`이라 불필요하게 넓은 권한을 갖게 됩니다.

```yaml
# 워크플로 전체 기본 권한을 read-only로 설정
permissions:
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    permissions:
      contents: read          # 코드 체크아웃
      id-token: write         # OIDC 토큰 발급 (Azure 로그인용)
      security-events: write  # CodeQL SARIF 업로드
      # pull-requests: write  # PR 코멘트가 필요한 경우에만 추가
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683
```

### 3-3. `pull_request_target` 함정

`pull_request_target`은 포크 PR에서도 베이스 브랜치의 시크릿에 접근할 수 있어 매우 위험합니다. 외부 기여자의 코드가 시크릿을 탈취하는 데 사용될 수 있습니다.

```yaml
# 위험한 패턴 — 절대 이렇게 쓰지 마세요
on:
  pull_request_target:
jobs:
  build:
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683
        with:
          ref: ${{ github.event.pull_request.head.sha }}  # 포크 코드 실행 + 시크릿 접근 = 위험
```

**대안**: 코드 실행이 필요하면 `pull_request` 이벤트를 사용하고, 라벨 추가 등 쓰기 권한이 필요한 작업만 `pull_request_target`으로 분리합니다.

### 3-4. OIDC 서브젝트 매핑 좁히기

Ch.6~7에서 OIDC로 Azure에 패스워드 없이 로그인하는 방법을 배웠습니다. Federated Credential의 Subject(sub) 매핑을 특정 브랜치·환경으로 좁히면 권한 남용을 막을 수 있습니다.

```bash
# 프로덕션 배포는 main 브랜치 + production 환경으로만 제한
az ad app federated-credential create \
  --id $APP_ID \
  --parameters '{
    "name": "github-oidc-main-production",
    "issuer": "https://token.actions.githubusercontent.com",
    "subject": "repo:Ai-Advanced/my-app:environment:production",
    "audiences": ["api://AzureADTokenExchange"]
  }'

# develop 브랜치용은 별도 Federated Credential로 분리
az ad app federated-credential create \
  --id $APP_ID \
  --parameters '{
    "name": "github-oidc-develop",
    "issuer": "https://token.actions.githubusercontent.com",
    "subject": "repo:Ai-Advanced/my-app:ref:refs/heads/develop",
    "audiences": ["api://AzureADTokenExchange"]
  }'
```

## 4. Azure Key Vault로 시크릿 관리

환경 변수나 GitHub Secrets에 직접 시크릿을 저장하는 방식은 감사 추적이 어렵고 순환(rotation)이 번거롭습니다. Key Vault를 중앙 저장소로 쓰면 이 문제를 해결할 수 있습니다.

### 4-1. Key Vault 생성

```bash
RESOURCE_GROUP="rg-myapp-prod"
LOCATION="koreacentral"
KEYVAULT_NAME="kv-myapp-prod-001"   # 전역 고유 이름, 3~24자

# Key Vault 생성 (RBAC 모드 권장)
az keyvault create \
  --name $KEYVAULT_NAME \
  --resource-group $RESOURCE_GROUP \
  --location $LOCATION \
  --enable-rbac-authorization true \
  --sku standard

# Soft Delete는 기본 활성화(90일), Purge Protection도 켜두기
az keyvault update \
  --name $KEYVAULT_NAME \
  --resource-group $RESOURCE_GROUP \
  --enable-purge-protection true
```

### 4-2. RBAC vs Access Policy (RBAC 권장)

| 항목 | Access Policy | RBAC |
|------|---------------|------|
| 관리 위치 | Key Vault 리소스 내부 | Azure AD RBAC |
| 감사 로그 | 제한적 | Azure Activity Log 통합 |
| 세분화 | Vault 단위 | 시크릿 단위 가능 |
| 권장 여부 | 레거시 | **신규 구성 시 권장** |

```bash
# 현재 로그인 사용자에게 Key Vault Administrator 역할 부여
MY_OBJECT_ID=$(az ad signed-in-user show --query id -o tsv)
KEYVAULT_ID=$(az keyvault show --name $KEYVAULT_NAME --query id -o tsv)

az role assignment create \
  --role "Key Vault Administrator" \
  --assignee $MY_OBJECT_ID \
  --scope $KEYVAULT_ID
```

### 4-3. 시크릿 저장 · 조회

```bash
# 시크릿 저장
az keyvault secret set \
  --vault-name $KEYVAULT_NAME \
  --name "DatabaseConnectionString" \
  --value "Server=myserver.database.windows.net;Database=mydb;..."

az keyvault secret set \
  --vault-name $KEYVAULT_NAME \
  --name "ExternalApiKey" \
  --value "sk-live-xxxxxxxxxxxx"

# 시크릿 조회 (값만 출력)
az keyvault secret show \
  --vault-name $KEYVAULT_NAME \
  --name "DatabaseConnectionString" \
  --query value \
  --output tsv

# 시크릿 목록 확인
az keyvault secret list \
  --vault-name $KEYVAULT_NAME \
  --output table
```

### 4-4. App Service에서 Key Vault Reference로 시크릿 주입

Key Vault Reference를 사용하면 앱 코드 변경 없이 환경 변수처럼 시크릿을 사용할 수 있습니다.

```bash
APP_NAME="myapp-prod"

# App Service의 System-assigned Managed Identity 활성화
az webapp identity assign \
  --name $APP_NAME \
  --resource-group $RESOURCE_GROUP

# Managed Identity Object ID 확인
WEBAPP_IDENTITY=$(az webapp identity show \
  --name $APP_NAME \
  --resource-group $RESOURCE_GROUP \
  --query principalId \
  --output tsv)

# Key Vault Secrets User 역할 부여
az role assignment create \
  --role "Key Vault Secrets User" \
  --assignee $WEBAPP_IDENTITY \
  --scope $KEYVAULT_ID

# 시크릿 URI 확인
SECRET_URI=$(az keyvault secret show \
  --vault-name $KEYVAULT_NAME \
  --name "DatabaseConnectionString" \
  --query id \
  --output tsv)

# App Settings에 Key Vault Reference 등록
az webapp config appsettings set \
  --name $APP_NAME \
  --resource-group $RESOURCE_GROUP \
  --settings "DATABASE_CONNECTION_STRING=@Microsoft.KeyVault(SecretUri=$SECRET_URI)"
```

앱은 `process.env.DATABASE_CONNECTION_STRING`으로 읽으면 됩니다. Azure가 런타임에 Key Vault에서 실제 값을 가져와 주입합니다.

### 4-5. Container Apps에서 Key Vault Reference 사용

```bash
CONTAINERAPP_NAME="mycontainerapp"

# Container Apps Managed Identity 활성화
az containerapp identity assign \
  --name $CONTAINERAPP_NAME \
  --resource-group $RESOURCE_GROUP \
  --system-assigned

CA_IDENTITY=$(az containerapp identity show \
  --name $CONTAINERAPP_NAME \
  --resource-group $RESOURCE_GROUP \
  --query principalId \
  --output tsv)

# Key Vault 접근 권한 부여
az role assignment create \
  --role "Key Vault Secrets User" \
  --assignee $CA_IDENTITY \
  --scope $KEYVAULT_ID

# 시크릿을 Container Apps Secret으로 등록 (Key Vault 참조)
az containerapp secret set \
  --name $CONTAINERAPP_NAME \
  --resource-group $RESOURCE_GROUP \
  --secrets "db-conn-string=keyvaultref:$SECRET_URI,identityref:system"

# 환경 변수로 매핑
az containerapp update \
  --name $CONTAINERAPP_NAME \
  --resource-group $RESOURCE_GROUP \
  --set-env-vars "DATABASE_CONNECTION_STRING=secretref:db-conn-string"
```

## 5. 컨테이너 이미지 보안

### 5-1. ACR Content Trust / Notary v2 개념

Notary v2(ORAS 기반)는 컨테이너 이미지에 서명을 붙여 무결성을 보장합니다. Azure Container Registry는 OCI Artifact 표준으로 서명을 저장합니다. 프로덕션 클러스터에서 서명된 이미지만 실행하도록 Ratify + Azure Policy를 함께 구성하는 것이 완전한 공급망 보안입니다. 자세한 구성은 공식 문서의 [ACR Notary v2 서명 가이드](https://learn.microsoft.com/azure/container-registry/container-registry-tutorial-sign-build-push)를 참고하세요.

### 5-2. Trivy로 CI에서 CVE 스캔

```yaml
# .github/workflows/container-security.yml
name: Container Security Scan

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

permissions:
  contents: read
  security-events: write

jobs:
  trivy-scan:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683  # v4.2.2

      - name: Build image
        run: docker build -t myapp:${{ github.sha }} .

      - name: Run Trivy vulnerability scanner
        uses: aquasecurity/trivy-action@6e7b7d1fd3e4fef0c5fa8cce1229c54b2c9bd0d8  # v0.24.0
        with:
          image-ref: myapp:${{ github.sha }}
          format: sarif
          output: trivy-results.sarif
          severity: HIGH,CRITICAL   # HIGH 이상만 보고
          exit-code: '1'            # 취약점 발견 시 파이프라인 실패
          ignore-unfixed: true      # 아직 픽스 없는 CVE는 제외

      - name: Upload Trivy scan results to GitHub Security tab
        uses: github/codeql-action/upload-sarif@4f3212b61783c3c68e8309a0f18a699764811cda  # v3.26.1
        if: always()
        with:
          sarif_file: trivy-results.sarif
```

### 5-3. Base Image 최소화

| 이미지 | 크기 (Node 20 기준) | 특징 |
|--------|---------------------|------|
| `node:20` | ~1.1 GB | 개발 편의 최대, 공격 면적 최대 |
| `node:20-slim` | ~240 MB | Debian 최소 패키지, 현실적 선택 |
| `node:20-alpine` | ~130 MB | musl libc, 일부 네이티브 모듈 빌드 문제 |
| `gcr.io/distroless/nodejs20-debian12` | ~110 MB | 쉘 없음, 공격 면적 최소 |

**권장 멀티스테이지 Dockerfile 패턴**:

```dockerfile
# 빌드 스테이지 (node:20-slim 사용)
FROM node:20-slim AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
RUN npm run build

# 실행 스테이지 (distroless 사용)
FROM gcr.io/distroless/nodejs20-debian12:nonroot
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
USER nonroot
EXPOSE 8080
CMD ["dist/main.js"]
```

## 6. Application Insights 통합

Application Insights는 Azure Monitor의 APM(Application Performance Monitoring) 컴포넌트입니다. 연결 문자열(Connection String) 하나로 앱에 붙입니다.

### 7-2. KQL 기본 문법 3가지

KQL(Kusto Query Language)은 Azure Monitor, Application Insights, Microsoft Sentinel에서 공통으로 사용합니다.

**① 기본 조회 + 필드 선택**

```kql
// 최근 1시간 HTTP 요청 로그 조회
AppServiceHTTPLogs
| where TimeGenerated > ago(1h)
| project TimeGenerated, CsMethod, CsUriStem, ScStatus, TimeTaken, CIp
| order by TimeGenerated desc
| take 100
```

**② 필터 + 문자열 조건**

```kql
// 5xx 에러 요청만 필터링
AppServiceHTTPLogs
| where TimeGenerated > ago(24h)
| where ScStatus >= 500
| project TimeGenerated, CsUriStem, ScStatus, TimeTaken
| order by TimeTaken desc
```

**③ 집계 + 시계열 시각화**

```kql
// 1분 단위 HTTP 상태 코드 분포 집계
AppServiceHTTPLogs
| where TimeGenerated > ago(6h)
| summarize
    RequestCount = count(),
    P95_ms = percentile(TimeTaken, 95),
    ErrorCount = countif(ScStatus >= 500)
    by bin(TimeGenerated, 1m), ScStatus
| render timechart
```

### 7-3. 5xx 에러 Alert Rule 설정

```bash
# Log Analytics 기반 Alert Rule 생성
az monitor scheduled-query create \
  --name "alert-5xx-errors" \
  --resource-group $RESOURCE_GROUP \
  --scopes $WORKSPACE_ID \
  --condition-query "AppServiceHTTPLogs | where ScStatus >= 500 | summarize ErrorCount = count() by bin(TimeGenerated, 5m)" \
  --condition-time-aggregation Count \
  --condition-operator GreaterThan \
  --condition-threshold 10 \
  --evaluation-frequency 5 \
  --window-size 5 \
  --severity 2 \
  --description "5분 내 5xx 에러가 10건 초과 시 경보" \
  --action-groups $(az monitor action-group show --name "ag-oncall" --resource-group $RESOURCE_GROUP --query id -o tsv)
```

## 9. 롤백이 필요한 3가지 시나리오

| 시나리오 | 증상 | 감지 방법 |
|----------|------|-----------|
| **성능 급락** | P95 응답 시간이 배포 전 대비 50% 이상 상승 | Application Insights 성능 메트릭, Alert Rule |
| **5xx 폭증** | 5분 내 5xx 에러가 평소 대비 5배 이상 증가 | Log Analytics Alert, 실시간 오류율 |
| **데이터 불일치** | 특정 API 응답에 null·빈 배열·잘못된 형식 반환 | 통합 테스트 실패, 고객 신고, 모니터링 알림 |

세 경우 모두 **먼저 롤백, 나중에 원인 분석**이 원칙입니다. 프로덕션에서 디버깅에 시간을 쓰는 것은 장애 시간을 늘릴 뿐입니다.

## 10. App Service 슬롯 스왑 롤백

슬롯 스왑은 DNS 수준에서 트래픽을 전환하기 때문에 다운타임 없이 롤백됩니다. 이전 배포본이 `staging` 슬롯에 그대로 남아 있기 때문에 재스왑만 하면 됩니다.

### 10-1. 슬롯 배포 + 검증 + 스왑 워크플로

```yaml
# .github/workflows/deploy-with-slots.yml
name: Deploy with Slot Swap

on:
  push:
    branches: [main]

permissions:
  contents: read
  id-token: write

jobs:
  deploy-to-staging:
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683

      - name: Azure login (OIDC)
        uses: azure/login@a65d910e8af852a8061c627c456678983e180302  # v2.2.0
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}

      - name: Deploy to staging slot
        uses: azure/webapps-deploy@de617f46172a906d0bb0fe7f0394e1b9c03a2e9c  # v3.0.1
        with:
          app-name: myapp-prod
          slot-name: staging
          package: ./dist

      - name: Wait for staging to be ready
        shell: bash
        run: |
          for i in $(seq 1 15); do
            STATUS=$(curl -s -o /dev/null -w "%{http_code}" \
              https://myapp-prod-staging.azurewebsites.net/health)
            [ "$STATUS" -eq 200 ] && echo "Staging ready" && exit 0
            sleep 20
          done
          exit 1

  swap-to-production:
    needs: deploy-to-staging
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Azure login (OIDC)
        uses: azure/login@a65d910e8af852a8061c627c456678983e180302
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}

      - name: Swap staging to production
        run: |
          az webapp deployment slot swap \
            --name myapp-prod \
            --resource-group rg-myapp-prod \
            --slot staging \
            --target-slot production
```

### 10-2. 문제 발생 시 즉시 롤백

스왑 방향을 반대로 실행하면 됩니다. 이전 배포본이 `staging`에 남아 있기 때문에 수 초 만에 롤백됩니다.

```bash
# 즉시 롤백 — staging(이전 프로덕션)과 production을 다시 교환
az webapp deployment slot swap \
  --name myapp-prod \
  --resource-group rg-myapp-prod \
  --slot staging \
  --target-slot production

echo "롤백 완료. 현재 production은 이전 버전입니다."
```

```yaml
# 롤백 전용 수동 워크플로
```

### 11-2. 이전 Revision으로 트래픽 전환

```bash
# 현재 Revision 목록 확인

  --name $CONTAINERAPP_NAME \
  --resource-group $RESOURCE_GROUP \
  --output table

# 출력 예시:
# NAME                           ACTIVE    TRAFFIC    CREATED
# mycontainerapp--v2-abc123      True      100        2024-01-15T10:30:00Z
# mycontainerapp--v1-def456      False     0          2024-01-14T09:00:00Z

  --resource-group $RESOURCE_GROUP \
  --revision-weight "$PREVIOUS_REVISION=100"
```

### 11-3. 자동 롤백 액션 예제

```yaml
# .github/workflows/deploy-container-app.yml (롤백 포함)
name: Deploy Container App with Auto-Rollback

on:
  push:
    branches: [main]

permissions:
  contents: read
  id-token: write

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    outputs:
      new-revision: ${{ steps.get-revision.outputs.revision }}
      prev-revision: ${{ steps.get-prev-revision.outputs.revision }}

    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683

      - name: Azure login (OIDC)
        uses: azure/login@a65d910e8af852a8061c627c456678983e180302
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}

      - name: Get current (soon-to-be-previous) revision
        id: get-prev-revision
        run: |
          PREV=$(az containerapp revision list \
            --name mycontainerapp \
            --resource-group rg-myapp-prod \
            --query "[?properties.active && properties.trafficWeight==\`100\`].name" \
            --output tsv | head -1)
          echo "revision=$PREV" >> $GITHUB_OUTPUT

      - name: Deploy new image
        run: |
          az containerapp update \
            --name mycontainerapp \
            --resource-group rg-myapp-prod \
            --image myacr.azurecr.io/myapp:${{ github.sha }}

      - name: Get new revision name
        id: get-revision
        run: |
          NEW=$(az containerapp revision list \
            --name mycontainerapp \
            --resource-group rg-myapp-prod \
            --query "sort_by([], &properties.createdTime)[-1].name" \
            --output tsv)
          echo "revision=$NEW" >> $GITHUB_OUTPUT

      - name: Health check with auto-rollback
        shell: bash
        run: |
          APP_URL="https://mycontainerapp.example.azurecontainerapps.io"
          MAX_RETRIES=15
          RETRY_INTERVAL=20
          PREV_REVISION="${{ steps.get-prev-revision.outputs.revision }}"

          for i in $(seq 1 $MAX_RETRIES); do
            STATUS=$(curl -s -o /dev/null -w "%{http_code}" --max-time 10 "$APP_URL/health")
            if [ "$STATUS" -eq 200 ]; then
              echo "Health check passed. Deployment successful."
              exit 0
            fi
            echo "Attempt $i: HTTP $STATUS. Waiting ${RETRY_INTERVAL}s..."
            sleep $RETRY_INTERVAL
          done

          echo "Health check failed. Rolling back to $PREV_REVISION..."
          az containerapp ingress traffic set \
            --name mycontainerapp \
            --resource-group rg-myapp-prod \
            --revision-weight "$PREV_REVISION=100"
          echo "Rollback complete."
          exit 1
```

## 12. Feature Flag로 배포와 릴리스 분리

### 12-1. Azure App Configuration + Feature Manager

Feature Flag는 코드에 기능을 미리 배포해 두고, 플래그 ON/OFF로 실제 사용자 노출을 제어하는 패턴입니다.

```bash
APPCONFIG_NAME="appconfig-myapp-prod"

# App Configuration 생성
az appconfig create \
  --name $APPCONFIG_NAME \
  --resource-group $RESOURCE_GROUP \
  --location $LOCATION \
  --sku standard

# Feature Flag 생성
az appconfig feature set \
  --name $APPCONFIG_NAME \
  --feature "new-checkout-flow" \
  --yes

# Feature Flag 비활성화 상태로 배포, 준비되면 활성화
az appconfig feature enable \
  --name $APPCONFIG_NAME \
  --feature "new-checkout-flow"

# 특정 사용자 그룹(베타 테스터)에만 활성화
az appconfig feature filter add \
  --name $APPCONFIG_NAME \
  --feature "new-checkout-flow" \
  --filter-name Microsoft.Targeting \
  --filter-parameters '{"Audience":{"Groups":[{"Name":"beta-users","RolloutPercentage":100}],"DefaultRolloutPercentage":0}}'
```

**Node.js에서 Feature Flag 사용**:

```typescript
import { AppConfigurationClient } from '@azure/app-configuration';
import { ConfigurationSetting } from '@azure/app-configuration';

const client = new AppConfigurationClient(
  process.env.AZURE_APPCONFIG_CONNECTION_STRING!
);

async function isFeatureEnabled(featureName: string): Promise<boolean> {
  try {
    const setting = await client.getConfigurationSetting({
      key: `.appconfig.featureflag/${featureName}`,
      label: '\0',
    });
    const flag = JSON.parse(setting.value ?? '{}');
    return flag.enabled === true;
  } catch {
    return false;   // 기본값: 비활성화
  }
}

// 사용 예시
app.get('/checkout', async (req, res) => {
  if (await isFeatureEnabled('new-checkout-flow')) {
    return res.redirect('/checkout/v2');
  }
  return res.redirect('/checkout/v1');
});
```

### 12-2. "배포는 매일, 릴리스는 필요할 때" 원칙

| 개념 | 정의 | 담당 |
|------|------|------|
| **배포(Deployment)** | 코드를 프로덕션 서버에 올리는 기술 행위 | 개발/DevOps 팀 |
| **릴리스(Release)** | 사용자에게 기능을 노출하는 비즈니스 결정 | 제품/비즈니스 팀 |

Feature Flag를 쓰면 배포는 CI/CD가 자동으로 매일 하고, 릴리스는 플래그 ON 하나로 언제든 할 수 있습니다. 문제가 생기면 플래그 OFF로 코드 재배포 없이 즉시 되돌립니다.

## 13. 데이터 마이그레이션과 롤백

### 13-1. Expand-Contract 패턴

데이터베이스 스키마 변경은 애플리케이션 롤백과 다릅니다. 한번 적용된 마이그레이션을 되돌리기 어렵기 때문에 **무중단 3단계 패턴**을 사용합니다.

```
Phase 1 (Expand): 새 컬럼/테이블 추가. 기존 코드는 여전히 동작.
                  ↓ 앱 v1 배포 (기존 컬럼 읽기/쓰기 + 새 컬럼에도 쓰기 시작)

Phase 2 (Migrate): 데이터 백필(backfill). 기존 데이터를 새 구조로 복사.
                   ↓ 앱 v2 배포 (새 컬럼만 읽기, 기존 컬럼에도 호환성을 위해 쓰기 유지)

Phase 3 (Contract): 기존 컬럼 제거. 앱이 완전히 새 구조만 사용.
                    ↓ 앱 v3 배포 (새 컬럼만 사용)
```

각 Phase 사이에 충분한 관측 기간을 두면 어느 단계에서든 이전 버전의 앱으로 롤백해도 데이터가 깨지지 않습니다.

## 15. 배포 안정성 체크리스트

### 보안

- [ ] CodeQL 스캔이 PR마다 자동 실행되고, High/Critical 취약점은 머지를 차단한다
- [ ] Secret Scanning + Push Protection이 조직 전체에 활성화되어 있다
- [ ] Dependabot이 npm, Docker, GitHub Actions 의존성을 주 1회 이상 업데이트한다
- [ ] 모든 third-party Actions가 버전 태그 대신 SHA로 고정되어 있다
- [ ] 워크플로에 `permissions:` 블록이 명시되어 있고 최소 권한만 선언한다
- [ ] `pull_request_target` 이벤트를 사용하는 워크플로가 없거나, 사용 시 코드를 실행하지 않는다
- [ ] OIDC Federated Credential의 Subject가 특정 브랜치·환경으로 좁혀져 있다
- [ ] 시크릿이 GitHub Secrets 대신 Azure Key Vault에 저장되어 있다
- [ ] App Service·Container Apps가 Managed Identity로 Key Vault에 접근한다
- [ ] Trivy 스캔이 CI에 통합되어 HIGH/CRITICAL CVE가 있으면 빌드가 실패한다
- [ ] 컨테이너 이미지가 distroless 또는 alpine 기반으로 최소화되어 있다
- [ ] 컨테이너가 non-root 사용자로 실행된다

### 모니터링

- [ ] Application Insights가 모든 프로덕션 서비스에 연결되어 있다
- [ ] Log Analytics Workspace로 App Service, Container Apps 로그가 통합된다
- [ ] 5xx 에러율 Alert Rule이 5분 이내에 알림을 보낸다
- [ ] P95 응답 시간이 임계값을 초과하면 Alert가 발생한다
- [ ] CPU·메모리 사용률 Alert Rule이 설정되어 있다
- [ ] Application Map으로 서비스 간 종속성이 시각화되어 있다
- [ ] 로그 보존 기간이 규정(보통 90일 이상)을 만족한다
- [ ] 배포 어노테이션이 Application Insights에 기록되어 배포 전후 지표를 비교할 수 있다

### 배포 프로세스

- [ ] App Service는 staging 슬롯을 통해 배포한다 (직접 프로덕션 배포 금지)
- [ ] Container Apps는 Multi-revision 모드로 운영한다
- [ ] 배포 후 헬스 체크 스크립트가 자동으로 실행된다
- [ ] 스모크 테스트가 배포 후 자동으로 실행된다
- [ ] 헬스 체크 실패 시 자동 롤백 스크립트가 워크플로에 포함된다
- [ ] 수동 롤백 워크플로(`workflow_dispatch`)가 준비되어 있다

### 릴리스 관리

- [ ] Feature Flag 시스템이 있어 배포와 릴리스를 분리할 수 있다
- [ ] 데이터베이스 마이그레이션은 Expand-Contract 패턴을 따른다
- [ ] 모든 마이그레이션은 롤백 스크립트(`down`)가 있다
- [ ] 배포 금지 시간대 정책이 팀 내에 문서화되어 있다
- [ ] 장애 발생 시 PIR(Post-Incident Review) 문서 작성 절차가 정해져 있다

## 16. 현업 팁

**팁 1. 배포 시간대 정책을 문서화하세요.**
금요일 오후, 공휴일 전날, 월말 결산 기간, 대형 이벤트(블랙프라이데이, 세일 기간)에는 프로덕션 배포를 금지하는 정책을 팀 위키에 명문화하세요. "언제 배포하지 않을지"를 아는 것이 "어떻게 빠르게 배포할지"만큼 중요합니다.

**팁 2. 롤백 시나리오를 정기적으로 연습하세요.**
슬롯 스왑 롤백, Revision 트래픽 전환을 스테이징 환경에서 분기마다 한 번씩 실행해 보세요. 실제 장애 상황에서 처음 해보는 것과 수십 번 해본 것은 심리적으로 완전히 다릅니다.

**팁 3. PIR(Post-Incident Review) 문화를 만드세요.**
장애가 발생하면 24~48시간 내에 PIR 문서를 작성하세요. 타임라인, 영향 범위, 근본 원인, 재발 방지 액션 아이템을 포함합니다. "누구의 잘못인가"가 아니라 "시스템이 왜 실패했는가"에 집중하는 Blameless 문화가 핵심입니다.

**팁 4. 알림 피로(Alert Fatigue)를 조심하세요.**
모든 것에 알림을 걸면 진짜 중요한 알림이 노이즈에 묻힙니다. Alert Rule을 추가할 때는 "이 알림을 받으면 즉각 대응할 것인가?"를 자문해 보세요. 그렇지 않다면 severity를 낮추거나 대시보드에서 참고 지표로만 쓰세요.

**팁 5. Key Vault 시크릿 순환을 자동화하세요.**
Managed Identity를 쓰더라도 외부 API 키처럼 서드파티가 발급한 시크릿은 주기적으로 순환해야 합니다. Azure Key Vault의 Rotation Policy를 설정하거나, Logic App·Function으로 순환 파이프라인을 구성하세요.

**팁 6. 배포 직후 10분을 집중 관찰하세요.**
배포가 완료된 직후 10분이 가장 위험한 시간입니다. Application Insights Live Metrics, Log Analytics를 열어두고 에러율, 응답 시간, CPU 사용률이 이상 없는지 능동적으로 확인하세요. 이 10분 동안은 다른 작업을 하지 마세요.

**팁 7. Copilot이 제안한 워크플로 코드도 보안 검토를 받으세요.**
GitHub Copilot이 생성한 Actions 워크플로에 `pull_request_target`이나 `secrets.*`를 과도하게 사용하는 패턴이 포함될 수 있습니다. 자동 생성 코드도 이 챕터의 보안 원칙을 적용해 검토해야 합니다.
